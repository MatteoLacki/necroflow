# Зачем нужен Necroflow?

Логику вы пишете на Python. Фреймворк берёт на себя кэш, DAG и генеалогию путей.

## Пайплайн — это обычный скрипт на Python

```python
@command("tr '[:lower:]' '[:upper:]' < {raw_text} > {processed_text}")
def process_text(raw_text: RawText, tool_config: ToolConfig):
    processed_text = output(ProcessedText)
    return processed_text

def my_pipeline(P: Pipeline, config: dict) -> None:
    P.raw = import_text(P, path=config["input"])
    P.processed = process_text(P, P.raw, P.tool_config)
    P.summary = summarize(P, P.processed)
```

- Результаты — обычные переменные, правила — обычные функции. Добавить шаг = добавить вызов и
  сделать небольшую локальную правку в использовании переменных, не переписывая имена файлов.
- Полноценный Python на этапе построения графа: циклы, условия, функции, тесты на pytest.
  Подпайплайны (`P.subpipeline`) — это обычные фабрики, а общие префиксы считаются один раз.
- Читается как нормальный процедурный код. Это важно при ревью: изменения остаются локальными,
  в местах вызова, поэтому легко проверить, правильно ли ИИ-агент понял замысел, — или написать
  логику самому и поручить реализацию правил кому-то другому. Пайплайн — это такой заголовочный
  файл C++ с намерением о том, как всё должно работать.

## Пути генерирует фреймворк

- Результат попадает в `nodes/{правило}/{provenance_hash}/{файл}`. Хеш (fingerprint v4)
  охватывает структуру рецепта, конфиг, shell и полную линию родителей.
- Одинаковая работа сходится в один каталог — в том числе между независимыми пайплайнами внутри
  одного DAG. Вы не проектируете ни таксономию имён файлов, ни wildcard-шаблоны.
- Рядом с результатом лежит `.rip/`: `dependencies.toml` (линия + SHA-256 потреблённых
  родителей), `graph.tgf` (DAG предков), `job.log`, `state`, `run.toml` (времена работы,
  размеры). Генеалогия путей путешествует вместе с файлом, а не сидит в центральной базе.
- То, что вы хотите смотреть, вы получаете копиями в `results/<job>/` под читаемыми метками, плюс
  `manifest.toml` (видимый путь, узел-источник, хеш содержимого). Копии — через reflink/CoW там,
  где это позволяет файловая система.

## Кэшируем по содержимому, а не по времени

- Пересборка родителя с идентичными байтами **не** инвалидирует потребителей: мы сравниваем
  SHA-256, а mtime нужен лишь для инвалидации быстрого пути.
- Состояние живёт в текстовых файлах, никакой базы данных. Зависший `running` после краха
  вынуждает перезапуск.
- `necroflow explain job.toml` говорит, что будет запущено и почему (по узлам); `doctor` делает
  предполётные проверки со стабильными кодами `NF_*`; `gc` чистит node store;
  `graph --json` / `outputs --json` / `provenance --json` — для инструментов и агентов.

## Типизированные результаты

- `NodeType` — это тип файла. Иерархию определяете вы; подтипы и объединения (альтернативы) типов
  работают как контракты формата, а `filename = None` даёт абстрактный контракт, только для
  входов.
- Фреймворк проверяет композицию во время построения пайплайна — ошибка прилетает раньше, чем
  стартует что-либо дорогое.

## Запуск

- Один `job.toml` описывает прогон; `__grid` разворачивает сетки параметров (подбор, много
  наборов данных) в отдельные задания с детерминированными метками.
- Локальный параллельный исполнитель с лимитами ресурсов (`threads`, `ram`, свои собственные),
  протоколом планировщика (по умолчанию FIFO), `--dry-run`, `--keep-going`, `repeat=N` и
  `autoclean` для промежуточных результатов.
- `RuleCall` атомарен: все со-выходы одного вызова кэшируются и выполняются вместе. Exit 0 при
  отсутствующем объявленном файле — это ошибка, а не успех.

## Как это соотносится с Nextflow (и Snakemake)?

Другая весовая категория и, что важнее, другая граница абстракции:

- Одна машина. Кластер мы не координируем — пока что.
- Контейнеры ортогональны: Necroflow не использует их каким-то особым образом. Можно запечатать
  весь проект в образ, а можно построить отдельные правила на `docker run` и соединить удобство
  Necroflow с воспроизводимостью настроенного снаружи окружения.
- Python вместо Groovy или DSL с wildcard-шаблонами: проще для разработчиков, для дата-сайентистов
  и для ИИ. Тесты и пайплайны по множеству наборов данных пишутся обычными средствами.
- Snakemake — ближайшая точка отсчёта, и он зрелый. Разница не в том, что там нельзя, — а в том,
  кто поддерживает таксономию путей и ограничения wildcard-шаблонов по мере накопления вариантов.
- Prefect показывает, что динамическая оркестрация на Python работает, но обобщённые задачи не
  дают ни типизированных файлов-результатов, ни путей, выведенных из линии происхождения.
- Небольшая кодовая база: ~5,6 тыс. строк в `src/`.

Минусы: это новое, так что вы автоматически становитесь early adopter'ом; нет ни HPC, ни облака;
нет экосистемы плагинов.

## Планы на ближайшее будущее

- Публикация — как раз пишу.
- Реанимация textual-менеджера процессов. Сейчас stdout правил уходит в `.rip/job.log` (потому
  что несколько правил работают одновременно); `tail` работает, но оконный менеджер — это всё же
  не то же самое.
- Разведка по SLURM — недалеко от меня есть суперкомпьютер, так что проверю, как он соотносится с
  тем, что уже готово.
